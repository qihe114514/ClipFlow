# Bilibili Login Redesign

## Goal

Replace the current manual-confirmation WebView login flow with an app-owned
login surface that supports two tabs:

- SMS login: mainland China phone number, Bilibili graphic verification when
  required, SMS code, and automatic login validation.
- QR login: a QR code generated by the Bilibili web login API using a desktop
  user agent, automatic status polling, and automatic login validation.

The existing encrypted local session format remains the storage boundary.

## Root Cause

The current flow loads `https://passport.bilibili.com/login` inside a WebView,
then waits for the user to press `login complete` before reading cookies. This has
three problems:

1. There is no page or navigation callback that establishes login completion.
2. Cookie reads are limited to a small set of WebView domains and are not
   tied to the login response that actually sets the session.
3. The WebView uses an Android user agent, while the requested web QR flow is
   exposed by Bilibili for a desktop user agent.

On newer Android WebView versions this makes a completed page and the later
CookieManager read an unreliable boundary. The fix is to consume cookies from
the login API flow, then validate them through `x/web-interface/nav` before
persisting them.

## Architecture

`BilibiliAccountAction` owns only dialog state and renders the Compose login
surface. A new Bilibili login data layer owns the protocol details:

- request captcha metadata and send the SMS code;
- submit the SMS code;
- generate and poll a web QR code with a desktop UA;
- collect transient `Set-Cookie` values from login responses;
- validate the resulting Cookie header and map the account profile.

The login data layer returns a small state/result model to the UI. It does not
write phone numbers, captcha values, or cookies to logs. It only calls
`BilibiliSessionStore.save` after `x/web-interface/nav` reports `isLogin=true`.

The existing parser and download code remain unchanged. The existing account
dialog and logout behavior remain unchanged, except logout continues clearing
the WebView CookieManager for compatibility with old sessions.

## Protocol

### SMS login

Use the current Bilibili web endpoints:

- `GET /x/passport-login/captcha?source=main_web`
- `POST /x/passport-login/web/sms/send`
- `POST /x/passport-login/web/login/sms`
- `GET https://api.bilibili.com/x/web-interface/nav`

The UI uses the native phone and SMS code fields. Bilibili's graphic
verification is not replaced by an invented local bypass: when the send-code
request requires it, the app opens only the verification surface, receives
the returned challenge values, and then continues the request. The web login
page itself is never shown as the form.

The send-code response provides a temporary captcha key. The login request
uses that key with the phone number and SMS code. Cookies from successful
responses are merged, validated, and saved.

### QR login

Use:

- `GET /x/passport-login/web/qrcode/generate?source=main_web`
- `GET /x/passport-login/web/qrcode/poll?qrcode_key=...&source=main_web`
- `GET https://api.bilibili.com/x/web-interface/nav`

The generate and poll requests use a desktop browser user agent and a
`Referer` for the Bilibili login page. The QR URL is rendered locally by the
app. Polling runs at one-second intervals until success, expiration, or a
network error. A successful poll captures the response cookies before account
validation.

## UI and state

The existing login dialog becomes a two-tab Compose surface:

- selected tab: `Phone login` or `QR login`;
- SMS tab: country code, phone field, SMS code field, send-code countdown,
  graphic verification entry point when required, login button, and error
  text;
- QR tab: QR image, remaining validity time, refresh button, polling status,
  and login success/error state.

Switching tabs cancels the inactive flow. Dismissing the dialog cancels all
polling and in-flight login work. The login button is disabled while the
current request is running. Successful validation closes the dialog and
refreshes the account action from the saved session.

Error messages distinguish invalid input, expired QR codes, rejected SMS
codes, required graphic verification, network failure, and Bilibili account
validation failure. No raw response body or Cookie value is shown to users.

## Testing and verification

Add pure unit coverage for:

- Cookie merging and duplicate removal;
- QR poll response mapping for waiting, scanned, expired, and success states;
- login state transitions and cancellation;
- validation refusing blank or unauthenticated navigation responses.

Run the focused unit tests first, then the complete `:app:testDebugUnitTest`
and `:app:assembleRelease` tasks serially using the repository's offline
Gradle 9.6 cache. Run `git diff --check` and inspect the final APK path.
Device acceptance is still required for Android 14 and Android 16 because
the available workspace does not provide those two physical devices.

## Constraints

- Keep `versionName` and `versionCode` unchanged.
- Do not add a remote login proxy or persist credentials outside the existing
  encrypted session store.
- Do not change Bilibili parsing, WBI signing, download, or media behavior.
- Keep the current uncommitted Cookie and parser-input changes unless the new
  login implementation makes a directly related adjustment necessary.
